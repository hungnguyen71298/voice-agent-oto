Voice Agent trên ô tô

Nói chuyện bằng giọng nói để điều khiển xe, tra sổ tay và hỏi thông tin. Cascaded pipeline trên Pipecat, TTS chạy local.

01Kiến trúc

mic ─► SileroVAD ─► STT ─► LLM (+tool calling) ─┬─► TTS (Piper, local) ─► loa
                    └── OpenRouter, 1 key ──┘   │
                                   │            └── lệnh điều khiển: đọc thẳng câu
                                   ▼                xác nhận, bỏ vòng LLM thứ 2
             tools/  vehicle mock · BM25 sổ tay VF 8 · search
  • Chỉ 2 lời gọi mạng mỗi lượt: STT và LLM. TTS, VAD, tool và knowledge base đều chạy trên máy.
  • Cascaded, không phải realtime API. Đề bài yêu cầu FAL < 2s, không yêu cầu realtime — và cascaded tính tiền theo lượt nói thật, không theo thời gian mic mở.
  • Đổi model bằng biến môi trường, không sửa code. Đã dùng đúng khả năng này để chọn cả ba chặng.

02First Audio Latency

Từ lúc hệ thống xác định người dùng ngừng nói, đến frame âm thanh đầu tiên phát ra loa.

1016ms · p50, lần chạy 1
1172ms · p50, lần chạy 2
2.7–3.2giây · p95
  • Đo bởi chính pipeline, đặt ngay trước transport output nên nó thấy đúng frame sắp ra loa.
  • p95 là lượt tra sổ tay — lượt duy nhất còn phải qua hai vòng LLM, vì kết quả tìm kiếm cần model tóm tắt.
  • Chưa trừ device output buffer (~20–40 ms), nên số báo lạc quan hơn thực tế chừng đó.

03Đo bằng cách nào

scripts/e2e.py dựng chính pipeline của sản phẩm — cùng VAD, cùng turn detection, cùng dispatch, cùng probe — chỉ thay mic và loa bằng file.

  • Audio bơm vào đúng tốc độ thật. Tua nhanh sẽ khiến VAD chốt hết lượt sớm và cho ra con số không ai đạt được ngoài đời.
  • Giọng người dùng commit sẵn trong repo → mọi lần chạy giống hệt nhau, không phụ thuộc dịch vụ nào.
  • Assert dựa trên sự kiện thật — tool nào chạy, agent nói gì — không dựa vào trạng thái xe.
  • Exit code khác 0 nếu bất kỳ lượt nào hỏng → chạy được trước mỗi lần demo.

07Tối ưu: bỏ vòng LLM thứ hai

Vòng đời chuẩn của một tool call là hai lời gọi LLM: một để quyết định gọi tool, một để đọc kết quả và diễn đạt.

Với lệnh điều khiển, kết quả {"temp": 22} chỉ có đúng một cách nói. Vòng thứ hai tốn nguyên một chặng mạng mà không thêm thông tin.

{"device": "ac", "status": "success", "speech": "Đã giảm còn 22 độ", "temp": 22}

app.py:  push_frame(TTSSpeakFrame(speech, append_to_context=True))
         result_callback(result, FunctionCallResultProperties(run_llm=False))
2517 → 984 ms · LLM p50
  • append_to_context giữ câu vừa nói trong lịch sử → lượt sau nói "tăng thêm hai độ nữa" vẫn hiểu.
  • Đường lỗi và tool tra cứu cố ý không có speech — chúng cần model diễn đạt. Ranh giới này có test giữ.

08Thêm tool = thêm một hàm

def set_ac(on: bool, temperature: int | None = None) -> dict:
    """Bật hoặc tắt điều hòa, có thể kèm đặt nhiệt độ.   ← description của tool

    Args:
        on: True để bật, False để tắt điều hòa.       ← description của tham số
        temperature: Nhiệt độ mong muốn, 16-30 độ C.
    """
  • Type hint → kiểu JSON schema. int | None → integer và không bắt buộc.
  • tools/ là Python thuần, không import Pipecat. Đổi framework chỉ phải viết lại schema.py + app.py.
  • dispatch() không bao giờ raise — LLM gọi sai tên, sai kiểu, thiếu tham số là chuyện thường; trả error dict để model tự sửa.
  • Mọi hàm validate xong mới mutate. Đây là lỗi đã xảy ra thật (set_ac bật điều hòa rồi mới từ chối nhiệt độ) và có test riêng.

09Knowledge base: dữ liệu thật

Sổ tay hướng dẫn sử dụng VinFast VF 8 (2026) — 12 chương, 530k ký tự, 850 chunk. Không mock.

  • BM25 in-memory: index dựng 250 ms, query 3 ms, 0 đồng, 0 lời gọi mạng. Đề bài mục 2.4 cho phép.
  • Hai chỉnh riêng cho tiếng Việt: chunk mang theo heading gần nhất (đoạn nói về sấy kính không chứa chữ "sấy kính" nào), và token gồm bigram âm tiết (áp_suất).
  • Dữ liệu thật lộ ra lỗi mà dữ liệu bịa không bao giờ lộ — chuyển sang sổ tay thật bắt được ngay hai lỗi retrieval.
  • Trần đã biết: vocabulary mismatch. Đường nâng cấp đã khảo sát: BM25 top-20 rồi rerank bằng baai/bge-m3, +100–200 ms chỉ trên nhánh KB.

10Hai lỗi chỉ lộ khi chạy thật

VAD chưa từng được nối

LocalAudioTransportParams(vad_analyzer=…) được Pipecat 1.7 nhận im lặng rồi bỏ qua — trường đó đã chuyển sang VADProcessor đứng riêng trong pipeline.

Code trông đúng, khởi động không cảnh báo gì, và pipeline câm hoàn toàn — kể cả đường mic thật.

Transcript không tới dashboard

User aggregator tiêu thụ TranscriptionFrame, nên probe đặt cuối pipeline không bao giờ thấy nó.

Mà hiển thị transcript là yêu cầu bắt buộc mục 2 đề bài.

84 unit test xanh không bắt được lỗi nào trong hai lỗi này. Một lần chạy thật thì bắt được cả hai.

12Đã làm và chưa làm

Đã có

  • Pipeline đầy đủ, FAL p50 ~1.0 s
  • Hội thoại đa lượt, hỏi lại khi thiếu thông tin
  • Sổ tay VF 8 thật + tool mở rộng bằng 1 hàm
  • Dashboard trực tiếp, một chiều nên không đụng vào FAL
  • Đánh giá tự động (mục 8), benchmark nhiều model (mục 8)
  • TTS chạy edge (mục 8), Docker build được
  • 84 test + lint, không cần key hay mic

Chưa làm, và biết vì sao

  • Barge-in: probe đã xử lý, chưa kiểm chứng bằng hội thoại thật
  • Câu đệm ("để tôi xem nhé") che 2 vòng LLM của nhánh tra cứu
  • Streaming ASR để STT chạy chồng lúc người dùng đang nói — phải đổi nhà cung cấp, /audio/transcriptions chỉ nhận file
  • Whisper local: đã thử, CPU 2063 ms — chậm gấp 3 lần gọi API
